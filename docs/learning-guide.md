# 从 Python 入门到 Ordra：订单 Agent 学习指南

本文保留从基础函数到完整 Agent 的课程说明。请先按[仓库 README](../README.md)安装依赖，所有命令均在仓库根目录执行。

新增 [数据分析实验](http://127.0.0.1:8000/code)：模型为模拟订单 CSV 生成 Python，在 Monty 独立工作进程中执行，收到运行错误或独立校验差异后最多修正两次，通过后提供 Markdown/CSV 报告。页面可查看每次代码与反馈，并提供明确标注的错误注入练习。仅运行 Python 子集，不向生成代码开放宿主文件、网络或业务系统；不是完整 Python 容器。记录单独保存，服务重启后的未完成分析需重新运行。关键实现、使用方法与验证步骤见 [第十四课：代码执行 Agent 与沙箱隔离](14_代码执行Agent与沙箱隔离.md)。`code_eval.py` 默认离线脚本模型加真实沙箱；`--live` 才调用现有 DeepSeek。

关于训练目标、工具调用样本、LoRA 训练入口与接回系统的说明，见 [本项目如何做模型微调](本项目如何做模型微调.md)。这是实施方案，当前尚未启动模型训练。

新增 Agent 执行策略对照实验：`.\.venv\Scripts\python.exe -X utf8 decision_eval.py`。复用现有执行与评测组件，在固定案例上重复比较当前策略、主管直接查询和独立子任务委派，记录任务通过率、策略遵循、无效调用、全部模型请求、用量与耗时。默认离线脚本验收；加 `--live` 才请求真实模型。每次使用临时数据，报告包含版本指纹和逐次证据，不自动修改正式聊天策略。运行和判读说明见 [Agent 执行策略实验](Agent执行策略实验.md)。

正式聊天已接入 Skills 按需加载：模型先看到本地技能名称和简介，通过 `load_skill` 读取本轮所需完整指引。内置退货处理、订单与政策核对两个技能；加载受预算与次数约束，版本和正文随检查点恢复，不增加工具或审批权限。执行记录显示加载结果和技能上下文用量，新回合重新选择技能。实现与关键代码、扩展方法、手动测试见 [第十三课：Skills 接入与按需加载](13_Skills接入与按需加载.md)。

Skills 现支持第三层引用读取：在 `SKILL.md` 中以 Markdown 链接声明 `references/*.md`，加载主指引后由模型单独调用 `read_skill_resource(name, path)`。只允许本技能清单内文件，最多 8 个引用、单文件 24000 字节、每任务 4 次读取尝试；正文通过预算检查后保存原版本，恢复不重读，下一回合不自动携带。引用不算业务证据，也不执行脚本。执行记录新增“技能引用读取”，与主指引一起计入“技能指引”预算。旧任务仍沿用原来的两层加载方式。

技能专项评测：`.\.venv\Scripts\python.exe -X utf8 agent_eval.py --suite skills`，默认运行脚本模型和真实本地 MCP，包含 7 个场景及 2 个关闭 Skills 的同题对照。覆盖主动选择、无需技能、错误路径、重复读取、预算不足和中断后版本恢复。加 `--live --case skill_auto` 可验证真实模型的选择；真实模式会产生模型调用费用。报告同时展示回答、选择规则、独立结果校验、请求数和已报告 token 用量；离线通过不代表真实模型总能选对。

正式聊天已增加执行反馈与动态重规划：工具失败、空检索、计划顺序错误或子任务缺信息时，下一次模型请求会带上简短的恢复建议和当前可用步骤。模型仍通过 `update_plan` 调整未完成步骤；已完成步骤与证据不能改写。仅改说明、重复相同证据不算进展；连续 3 批无进展时保存停止说明与历史，执行记录标为“无新进展，已停止”，不再自动调用模型或工具，用户可直接补充信息。首次规划、加载新工具不计为停滞；失败后允许一次计划修订过渡，但不重置已有计数。计数和证据指纹随检查点恢复。

执行记录页可查看反馈原因、调整步骤与恢复结果。检测依据是新证据和实际完成的步骤，语义上的偏题仍由结果校验器检查；恢复跟踪本身不额外请求模型。反馈与工具结果共用上下文预算，预算很紧时会缩短附加反馈，必要时只保留原工具错误和轨迹记录。新功能离线验证：`.\.venv\Scripts\python.exe -X utf8 -m unittest discover -s tests -p test_agent_recovery.py -v` 和 `.\.venv\Scripts\python.exe -X utf8 -m unittest discover -s tests -p test_recovery_graph.py -v`；使用临时数据，包含真实本地 MCP 调用，不消耗聊天模型额度。此功能增强正式 `/` 聊天入口；独立 `/graph` 实验仍保持原有对照流程。

这份练习让你在“查询订单”的具体场景里学够用的 Python。有 TypeScript 基础的读者可以从中文注释和运行示例开始。

**课程范围：Python 基础、DeepSeek 单次问答、订单工具调用、多轮对话、流式输出、FastAPI 网页接入、SQLite 会话持久化、上下文管理与历史原文检索。** `01`、`02` 使用本地模拟数据；`03` 至 `07` 的模型功能会向 DeepSeek 发起真实请求。`08_context_demo.py` 和 `09_history_demo.py` 默认离线，添加 `--live` 才会请求模型。

历史检索见 [第九课：历史检索工具](09_历史检索工具.md)。Agent 可按需搜索当前会话的 SQLite 原文，找回摘要遗漏的信息；检索结果计入现有 token 预算。先运行 `.\.venv\Scripts\python.exe -X utf8 .\09_history_demo.py`，再用 `--live` 观察模型主动调用工具。第八课的[滚动摘要与上下文管理](08_上下文管理.md)继续生效。

网页历史搜索已补充关键词与本地中文语义混合检索，第九课演示仍保留关键词版本。新环境安装 `requirements.txt` 后，运行一次 `.\.venv\Scripts\python.exe -X utf8 .\local_embeddings.py` 下载模型；聊天时在本机生成向量，无需新的 API Key。模型缺失或不可用时自动回退到关键词，`/api/health` 中的 `semantic_status` 可查看状态；原文来源、会话隔离与 token 预算继续生效。

网页还支持业务知识库：`search_knowledge` 检索 `knowledge/` 内的 UTF-8 Markdown/TXT，结合订单信息解释政策。当前资料均为**明确标注的示例政策，不代表真实商家承诺**；可以用自己的业务资料替换，编辑或删除后下次检索立即生效。回答下方“检索参考资料”保存当时的原文片段，点击标题可查看对应版本的全文；资料已改动时会提示版本变化。该工具只读资料，不能执行退货、退款或改地址。

知识库与历史检索共用本地 Embedding，并合计限制为每轮最多3次检索；返回片段纳入 token 预算。当前支持最多100份资料，单文件128 KiB、总计512 KiB，超过限制会明确报错。只索引 `knowledge/`，不读取整个项目；知识库资料会作为模型请求的上下文发送给配置的聊天模型。

业务知识库的操作说明见 [第十课：RAG 使用教程](10_业务知识库RAG使用.md)，包含网页提问、查看来源、添加与更新资料、Embedding 和联网调用的分工，以及常见问题排查。

网页已支持本地模拟退货申请：说明订单号和原因后，Agent 提出待执行参数，网页批准后生成预览卡片；点击“确认提交”才创建申请，返回编号并可继续查询状态。预览和申请保存在 SQLite，刷新或重启后恢复；重复确认返回同一编号。后续成功对话会使旧未确认预览失效，删除会话也会删除其中的模拟申请。点击网页右上方“售后审核”可查看申请，由人工选择通过或拒绝并填写原因；结果保存后不能覆盖修改，Agent 查询时会读取最新状态与审核原因。审核记录单独保存，不改写原聊天内容；审核通过不代表已退款，没有接入真实售后系统。

Agent 工具执行已接入 `tool_runtime.py`：同批独立只读查询最多并行 3 项，预览操作保持串行；依赖查询结果的工具由模型在下一次决策中调用。每项工具的执行、重试与退避共用 8 秒预算，连接故障或数据库忙最多尝试 2 次，参数错误和业务拒绝不自动重试；超时停止等待并丢弃迟到结果，本轮不重复相同的失败调用。每回合最多调度 12 项工具，历史与知识库共用 3 次有效检索请求额度（失败也占额度）。接口的 `execution` 字段和流式 `tool_execution` 事件包含调用、尝试、重试与并行统计；不改写完整聊天历史。

复杂请求可通过 `update_plan` 维护最多 4 步的执行计划，网页实时显示进度。`agent_plan.py` 校验依赖关系，只有当前步骤声明的工具能够执行，完成步骤须引用成功结果中的 `_tool_call_id`；模型负责判断这些结果是否足以完成任务。未完成步骤可以附说明修订，已完成步骤和证据保留。计划全部完成或明确标记阻塞后才能结束，提前结束会获得一次纠正机会；普通请求最多 4 次模型决策，有计划的请求最多 10 次。计划最多接受 6 次普通更新，转入阻塞仍可退出；阻塞说明经结果校验后保存为回复，用户可补充信息。计划更新不占用 12 次业务工具额度，原 token 和检索预算仍生效。模型上下文仅保留最新有效计划和最近校验反馈，所有业务结果仍保留；完整计划快照随成功回合保存在原工具消息中，刷新后恢复。

滚动摘要支持超长单回合：完整回合无法放入摘要请求时，将该回合的 JSON 原文按请求预算分块，依次合并摘要；单条工具结果过长也可处理。片段文本只是摘要模型的历史数据，不作为可执行工具消息。已完成片段的摘要与位置保存在检查点中，中断后从保存位置继续；全部片段成功后才更新整轮覆盖位置。原始历史仍完整保存，当前回合与近期完整回合的预算规则保持不变。

应用默认上下文预算为 `32768`，扣除回答与安全预留后可用输入为 `32000`；显式配置 `AGENT_CONTEXT_TOKENS` 仍优先。当前任务达到可用输入的 75% 时，`active_context.py` 会把较早的完整工具批次整理为结构化阶段记录，省去重复包装和过程说明，保留实际参数、工具结果、证据编号与来源。最新计划、技能全文、审批相关消息及最近完整批次继续保留；这一过程由程序完成，不增加模型调用。历史回合仍使用原有滚动摘要。

预算处理先压缩当前任务，再考虑裁剪检索片段；可选的恢复提示不会优先挤掉事实。完整检索原文在裁剪前保存，历史记录和答复校验使用原始证据。若整理后仍无法放入检索内容，会明确提示处理空间不足并结束本轮自动重试，不把它当作无命中反复换词查询。提高服务的上下文预算后恢复旧任务，可采用更大的输入额度，原模型/工具调用、审批和恢复次数不重置。

等待用户补充信息的说明若未通过结果校验，可依据已有证据改写一次。该请求不提供工具，任务保持阻塞；请求前记录已消耗额度，中断恢复也不会重新调用工具或反复改写。

网页执行会保存检查点：工具批次完成及每批摘要成功后保存进度，模型/工具调用前保存已预留额度。刷新或重启服务后，可点击“继续执行”复用已保存结果；也可“放弃本次执行”后重新提问。每个会话最多一个未完成任务，最多恢复3次，恢复不重置原任务额度；未保存的只读工作可能重做。完整答复、摘要、退货预览与检查点清理同事务提交，提交失败可直接重试保存，预览编号保持一致。存在未完成任务时，同一会话的新问题、申请确认和审核暂缓；删除或重置会话会清理检查点。

工具执行前支持人工介入：`human_approval.py` 的服务器策略决定审批范围，当前用于 `prepare_return_request`。网页可批准、修改参数后批准或拒绝；等待时不继续请求模型，刷新与重启后保留审批。决定绑定会话、任务及审批 ID，重复和过期决定被拒绝；修改使用同一工具参数校验。处理最后一项审批后的首次继续不占断连恢复次数，各项任务预算不重置。拒绝不会执行该调用，模型也不能自行换参数重试；决定与原参数保存在工具结果中。审批只允许生成预览，正式模拟申请仍需卡片确认。模型额度耗尽时页面禁用无效恢复并说明原因。

执行轨迹已接入 [执行记录页面](http://127.0.0.1:8000/runs)：按会话查看模型提议、工具参数与结果、计划、人工决定、失败和恢复，并统计已报告 tokens、请求与调度尝试。恢复沿用同一个任务编号，最终状态与历史同事务提交。旧任务不补造记录；旧检查点恢复时保留累计统计并注明记录起点。轨迹省略提示词、摘要和检索正文，不包含模型隐藏思考；删除或重置对话同步清理记录。调度尝试包括参数预检和拒绝处理，不等于业务函数一定已执行。

执行记录现在还显示每次模型请求的上下文预算：区分主管、子 Agent、历史摘要和结果校验，列出估算输入、可用预算、系统提示词、工具定义、历史摘要、近期消息和工具结果的组成，以及上下文组装前后减少的估算量。摘要和校验模型以 JSON 包装的资料显示为“结构化任务资料”。预检只保存数字，不保存正文；“准备就绪”不等于请求已完成，超限则显示“预算已拦截”。估算采用现有 UTF-8 保守算法，实际计费用量仍以服务端 usage 为准。旧记录不补造，新请求及恢复后的请求开始记录，恢复不会重复已有事件。

网页 API 默认启用结果校验（`result_verification.py`）：候选答复暂存于检查点，经一次独立、无工具的模型请求核对目标和执行证据后才展示。服务器另行检查当前证据 ID、预览订单与待确认状态。发现问题时最多修正两次，每次增加一次主模型决策额度；工具、检索和审批额度仍共享，完成的计划只允许补充只读查询。最多尝试三次校验，恢复不重置次数；校验服务异常可继续，已通过的候选在保存重试时不重复请求。仍无法核实时保存明确说明和 `unverified` 执行状态，不发布本轮未核实预览。执行记录可查看校验次数、待核对项数量与额外 token 用量。语义核对依赖模型判断，不能保证发现所有错误。

多 Agent 协作已接入 `subagent_runtime.py`：主管可通过 `delegate_tasks` 委派独立的订单查询和知识检索，子 Agent 只接收本次问题与明确交接的资料，不复制主管的完整历史。每回合最多两个子任务，每项最多三次模型请求；主管与子 Agent 共用原有工具、检索和并行额度。实际工具证据与结构化结论一同交回主管，最终答复仍经过结果校验；退货操作仍需人工审批。检查点分别保存各子任务，中断恢复时复用已经完成的结果；一个子任务失败会保留另一项成果。聊天与执行记录显示角色、状态和子模型用量，知识来源刷新后仍可查看。子 Agent 会产生额外模型请求，当前使用同一配置模型、隔离的消息上下文。

子 Agent 的接入方式与关键代码见 [第十一课：子 Agent 接入与任务委派](11_子Agent接入与任务委派.md)，包含主管工具注册、独立消息、工具权限、结构化交接、共享预算、恢复与扩展位置。

子 Agent 回传多次知识检索结果时，主管按剩余 token 预算整理请求视图：相同来源、版本和原文只传一份，引用仍对应实际工具调用；完整原文可用时省去子模型的重复解释。完整历史、检查点、来源卡片和结果校验器仍保留原始证据。旧的未完成交接在恢复时同样生效，无需重复检索。不同版本、检索失败与资料不完整的标记不会被合并或抹去。

自动评测入口为 `agent_eval.py`，默认用脚本模型与真实本地工具检查 12 个流程，JSON 与 HTML 报告写入 `.local/evals/`；离线通过率不代表真实模型能力。加 `--live` 才调用配置模型，例如 `.\.venv\Scripts\python.exe -X utf8 .\agent_eval.py --live --case order_query`。两种模式都使用临时业务数据库与示例知识库；任一场景不符合预期时退出码为 1，故障场景会明确注入模拟故障。

连续对话评测使用 `agent_eval.py --suite multiturn`，每个场景在同一会话中运行3轮，覆盖前文指代、订单更正、长历史摘要后委派、故障后继续；`--suite all` 一起运行原12项和新4项。可用 `--case mt_correction` 单独选择，添加 `--live` 请求真实模型。长历史场景明确标注预置的16轮合成背景，使用临时数据和8192上下文压力预算。报告包含逐轮回答、实际工具证据、请求预算组成、请求数、已报告用量与耗时。过程分数是已定义规则约束的满足比例，检查目标订单、实际证据、参数错误和同轮重复检索；不要求唯一执行顺序，跨轮刷新查询允许重复。规则分数不代表全面语义准确率，未报告用量或未配置价格不会当作零成本。

正式[订单客服](http://127.0.0.1:8000/)已迁入 LangGraph：`full_agent_graph.py` 用独立节点组织上下文、模型决策、工具、子 Agent、人工审批和结果校验，`agent_service.py` 保留公共入口与工具适配。多轮历史、滚动摘要、工具预算、审批规则和子 Agent 能力继续使用。`/api/health` 中的 `agent_engine` 为 `langgraph`。

正式聊天默认启用 **MCP 接入与工具按需发现**。`mcp_tool_server.py` 使用官方 MCP Python SDK，通过本机标准输入输出提供只读订单和知识检索；应用负责启动、关闭和故障后的有限重连，无需另开服务端口。知识库沿用现有 keywords/hybrid 配置，本地 Embedding 不变。工具目录和参数来自真实 `tools/list`，调用通过 `tools/call`；当前只接入代码中明确允许的两项 MCP 能力，没有远程服务或任意命令配置。

主 Agent 初始看到核心规划/委派工具、`discover_tools` 和简短业务目录；需要查询时先用 `discover_tools(names=[...])` 选择能力，下一次模型请求才携带所选工具的完整参数定义。发现和业务调用必须分开，未加载工具会被拒绝。子 Agent 已按职责收窄，直接获得唯一职责工具，实际订单/知识调用仍通过 MCP。每次执行独立保存已加载名称和定义指纹；已保存的结果不因恢复而重放，定义变化会拦截旧调用。

每次主管请求同步本轮已加载工具、当前计划步骤缺少的工具及剩余发现次数，避免把历史回合的加载记录当成本轮状态。发现参数只列出尚未加载的工具；重复发现明确返回 `already_loaded`，仍计入次数且不算业务进展。纠正混合调用或完成对应工具加载后，过期恢复提示会清除，原有防空转计数继续保留。

在[执行记录](http://127.0.0.1:8000/runs)查看“工具按需加载”、工具来源及每次“模型上下文预算”中的实际工具列表和“工具定义”token 估算。每轮最多3次发现，独立于业务工具额度；每次发现最多补充一个模型请求名额，所有实际请求照常计入记录和预算。工具数量较少时，新增发现请求可能提高总 token 和耗时，不能把单次工具定义减少当作总成本下降。

`AGENT_TOOL_MODE=mcp` 是正式应用默认值，设为 `local` 可使用原本地直接调用与完整工具定义路径作对照。旧检查点沿用原路径，新 MCP 检查点需要在 MCP 模式继续。原 `agent_eval.py` 和 `langgraph_eval.py` 保留 local 基线；新增对照入口运行真实本地 MCP、临时业务库和示例资料：

## 用 TypeScript 经验理解 Python

| Python | 这里可以怎样类比 | 需要注意的区别 |
|---|---|---|
| `name = "小林"` | 给变量赋值 | 不写 let／const；大写命名也不会强制变成不可变值 |
| `dict` | 表示记录时类似普通对象 | 通常用 `order["status"]`，不是 `order.status` |
| `list` | 类似数组 | 获取长度用 `len(messages)` |
| `None` | 这里表示没有值，类似 null | 用 `is None` 判断 |
| `True`／`False` | 布尔值 | 首字母大写 |
| `def` | 定义函数 | 冒号和缩进划定函数体 |
| `order_id: str` | 参数类型标注 | 标注本身不会在运行时拦截错误输入 |
| `-> dict` | 返回类型标注 | 不是箭头函数，而是返回值类型提示 |
| `f"订单：{order_id}"` | 类似模板字符串 | 前缀为 f，占位表达式直接写在花括号中 |
| `json.dumps()` | JSON.stringify | 返回字符串，不会自动保存文件或发请求 |
| `json.loads()` | JSON.parse | 可能产生 JSONDecodeError |
| `try / except` | try / catch | 建议捕获明确的异常类型 |

Python 也有“真值”判断：空字符串、空列表和空字典会被视为假；这点与 JavaScript 中空数组、空对象为真不同。不要把熟悉的 JS 判断规则全部照搬。

`for item in items` 会直接取得列表元素，类似 JS 的 `for...of`；遍历字典时默认取得键。`if`、`for` 的缩进块也不会创建 JS 中由 let 提供的那种块级作用域。

## 什么是虚拟环境

项目的 `.venv` 提供独立的解释器入口和依赖安装位置。它隔离依赖，但仍然可以访问当前用户有权限访问的资源。

建议使用 Python 3.12 或更新版本；当前开发环境已在 Python 3.14 验证。安装要求与启动步骤见[仓库 README](../README.md)。虚拟环境不随源码发布，移动项目目录后也应重新创建：

~~~powershell
python -m venv .venv
~~~

其中 `-m venv` 表示“让这个 Python 运行标准库中的 venv 模块”。本项目直接使用下面这个入口，可以明确选择项目环境：

```powershell
.\.venv\Scripts\python.exe -X utf8 --version
.\.venv\Scripts\python.exe -X utf8 -m pip --version
```

`pip` 用于安装第三方库。第二课安装 `openai` 和 `python-dotenv`；第五课直接使用随 SDK 安装的 `httpx2` 识别流式连接异常；第六课增加 FastAPI、Uvicorn、Pydantic 和 AnyIO。这些直接依赖的版本记录在 `requirements.txt`。以后重建环境时，执行下面的命令恢复这些依赖：

```powershell
.\.venv\Scripts\python.exe -X utf8 -m pip install -r requirements.txt
```

不要把 `.venv` 内自动生成的文件当作本课需要学习的代码。

## 实际调用过程

执行 `02_query_order.py O1001` 时：

1. Python 读取脚本，导入 json、sys 和同目录的 get_order 函数。
2. 文件底部发现自己是直接运行的入口，于是调用 main。
3. main 从 `sys.argv[1]` 取得字符串 O1001。
4. get_order 检查类型，清理空格，将订单号转成大写，然后查询字典。
5. 查询函数返回字典，main 将其转换为可读的 JSON 字符串并打印。
6. main 返回退出码，程序结束。

`return` 是把值交给调用者；`print` 是显示到终端。后面接模型时，会使用函数返回值构造工具结果，终端里的打印文字不会自动进入模型上下文。

## 各课如何连接起来

`02_query_order.py` 能调用订单函数，`03_model_chat.py` 能向模型提问。第三课的 `04_order_agent.py` 已将这两块能力连接起来。

程序给模型描述函数的用途与参数，接收模型提出的工具调用，检查参数后执行本地函数，再把结果发回模型。

```text
第一课：终端输入订单号 → 程序直接调用 get_order → 打印结果

第二课：终端输入问题 → DeepSeek → 打印回答

第三课：自然语言问题 → 模型提出工具调用 → 程序执行 get_order
                                       ↓
                           把结果交回模型 → 生成回复

第四课：保留本轮完整消息 → 等待下次输入 → 携带历史继续处理

第五课：逐片接收并显示 → 收齐工具参数 → 完成检查 → 保存完整回复

第六课：网页发请求 → FastAPI 找到会话 → Agent 事件 → SSE 逐段显示

第七课：完整回合写入 SQLite → 重启后按编号恢复 → 继续追问

第八课：token 预算 → 滚动摘要 + 近期完整回合 → 原始历史与摘要一起保存

第九课：上下文缺少旧细节 → 模型请求 search_history → SQLite 原文 → 有依据的回答
```

第三课先做到：能指出函数真正执行的位置，能解释工具结果怎样加入下一次模型请求，并能在终端观察订单不存在或多笔查询时的处理过程。

第四课再用 `/history` 观察上下文，理解普通回复也需要保存，以及失败回合为什么不加入已完成的历史。

第五课理解流式显示与完整消息保存的区别。第六课把同一个流程接到 HTTP 和网页上；第七课将完整消息持久化，理解提交成功才报告完成，以及失败时的事务回滚。
