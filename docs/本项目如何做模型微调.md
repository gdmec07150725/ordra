# 本项目如何做模型微调

这是后续实施方案，当前未执行模型训练，也未实现训练数据导出管线。

## 先确定训练目标

我们希望模型更稳定地选择下一步动作：先发现再调用工具，缺信息时追问，正确更新计划，收到工具错误后采取有效的恢复动作。订单状态、库存、退款政策仍由业务工具和 RAG 提供。微调会调整模型参数；修改提示、运行评测、增加知识文档都不会自动改变参数。

目前 `api_app.py` 使用 `AsyncOpenAI` 客户端连接 DeepSeek 推理接口，模型名称来自 `DEEPSEEK_MODEL`。这个调用路径没有训练功能。若使用托管微调，需要另外确认提供商支持的训练服务；若使用开放权重模型，可以在独立 GPU 环境中进行 SFT（监督微调）和 LoRA 训练。

LoRA 冻结原模型权重，训练附加的低秩参数。训练结果通常是适配器，推理时要与匹配的原模型一起加载，或先合并权重。[PEFT LoRA 文档](https://huggingface.co/docs/peft/main/en/conceptual_guides/lora)

## 数据按每次决策整理

不能只保存“用户问题 → 最终答案”。Agent 的训练样本需要包含这一次请求实际看见的消息、可用工具定义、技能指引、检索结果，以及人工核对后的正确下一步。

| 当时可见的状态 | 期望学习的下一步 |
| --- | --- |
| 用户查询 O1003，工具定义中尚无 get_order | 单独调用 discover_tools，names 为 ["get_order"] |
| 已发现 get_order，本次请求已提供它的参数定义 | 调用 get_order，order_id 为 "O1003" |
| 工具返回 O1003 已签收 | 根据结果答复，不编造物流细节 |
| 用户想退货，但缺少具体退货原因 | 追问原因，不猜测、不生成退货预览 |
| blocked 步骤错误地携带 evidence，校验器返回修复提示 | 提交 evidence 为 [] 的完整计划，并在顶层 note 说明缺失信息 |

每次决策拆成一条训练样本，避免把后续才加载的工具定义提前放进第一条样本。可以使用 `prompt` 保存输入消息、`completion` 保存正确的下一条 assistant 消息、`tools` 保存当时的工具定义；具体工具调用编码还要匹配所选模型的聊天模板。

现有评测报告用于定位问题，并非完整训练数据集：它没有保留每次模型请求的全部正文，公开轨迹也会裁剪部分工具结果。后续需要增加专门的请求快照导出和人工标注流程。包含错误动作的成功会话也不能整段直接作为正例；错误可以放在输入里教恢复，但监督目标应是审核后的正确动作。

训练前对真实数据去标识化、移除密钥，并按会话及问题变体分组划分训练集、验证集和保留测试集。同一问题的重复运行应放在同一组。执行策略评测中的 54 次运行对应 6 类固定问题的重复实验，不能视为 54 类独立任务，也不能同时用于训练与泛化验证。

## 训练代码的核心形态

下面仅展示训练入口，不是已经接入项目的可执行任务。`train.jsonl` 和 `validation.jsonl` 需要先完成上述导出、审核、分组和模板验证；模型路径、学习率、批次及长度策略需要根据模型和 GPU 确定。训练依赖应放在独立环境，不直接改客服服务的运行环境。

```pyt
from datasets import load_dataset
from peft import LoraConfig
from trl import SFTConfig, SFTTrainer

data = load_dataset("json", data_files={
    "train": "train.jsonl",
    "validation": "validation.jsonl",
})

trainer = SFTTrainer(
    model="/models/selected-tool-calling-model",
    train_dataset=data["train"],
    eval_dataset=data["validation"],
    args=SFTConfig(
        output_dir="outputs/customer-agent-lora",
        completion_only_loss=True,
        max_length=None,
        per_device_train_batch_size=1,
        gradient_accumulation_steps=8,
        num_train_epochs=1,
        learning_rate=1e-4,
        report_to="none",
    ),
    peft_config=LoraConfig(
        task_type="CAUSAL_LM",
        r=16,
        lora_alpha=32,
        target_modules="all-linear",
    ),
)
trainer.train()
trainer.evaluate()
trainer.save_model("outputs/customer-agent-lora")
```

这里采用 prompt/completion 数据格式，只对 completion 计算训练损失。`max_length=None` 避免默认截断破坏工具调用与结果的配对，但要求预先筛选长度、确认显存足够；它不是线上取消上下文预算。TRL 支持工具调用数据及 PEFT 适配器训练。[TRL SFTTrainer 文档](https://huggingface.co/docs/trl/sft_trainer)

训练的过程是：模型预测目标回复或工具调用的 token，计算与标注答案之间的损失，再通过反向传播更新 LoRA 参数。一次普通聊天请求不会执行这个过程。训练损失下降也不等于 Agent 业务任务一定更可靠。

## 接回系统并验证

1. 部署原模型与适配器，提供支持工具调用、流式事件和用量统计的模型接口。
2. 将 `api_app.py` 中目前固定的模型服务地址改成可配置项，接入新接口；核对所选模型的工具调用格式。这里目前还没有实施，不能只改模型名称就当作完成部署。
3. 保留 LangGraph 编排、MCP 工具发现、Skills、结果校验、审批和上下文预算。模型变了，运行时的权限与证据校验仍然需要。
4. 用同一份未参与训练的保留测试集，对比原模型和微调模型。复用 `decision_eval.py` 的任务成功率、无效调用、重复调用、请求数、token 和耗时统计，并检查缺信息、故障恢复与越权操作。

当前优先把已复现的调用协议问题修好、把评测基线稳定下来。之后最有价值的微调准备工作是“逐次请求快照与人工纠正数据集”，再决定是否值得投入训练。
