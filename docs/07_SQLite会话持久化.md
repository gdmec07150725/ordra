# 第七课：用 SQLite 保存会话，重启后继续聊

> 本文按课程阶段讲解；请在仓库根目录执行命令。安装与当前功能以[仓库 README](../README.md)为准，早期章节中的简化流程不代表最终实现。

> 后续版本：[第八课](08_上下文管理.md)已加入 token 预算、滚动摘要与近期完整回合。完整历史仍按本课方式保存；摘要另存于 context_memory 表，与成功回合一同提交。下文“携带完整历史请求模型”描述第七课阶段，当前请求由预算动态决定。

第六课把 Agent 接到了网页上，但历史只存在 Python 进程的内存中。这一课把完整对话保存到磁盘，并提供历史列表：后端重启、关闭标签页后都可以重新选择旧会话继续追问。“新对话”创建独立的会话，保留原来的记录。

项目仍在 `.`，继续运行 `07_api_server.py`。这一课没有新增启动脚本，也不需要安装数据库服务或新的 pip 依赖。本机 Python 已提供 `sqlite3` 模块。

## 1. 先体验一次“重启后继续聊”

在 PowerShell 中启动服务；如果页面已经能打开，不用重复启动：

```powershell
# 在仓库根目录运行
.\.venv\Scripts\python.exe -X utf8 .\07_api_server.py
```

打开[聊天页面](http://127.0.0.1:8000)。历史列表按创建时间从新到旧排列，用第一条已保存的问题作标题，空会话显示“新对话”。点击列表项可以切换；生成回复期间暂时锁定切换和新建。先完成下面的操作：

1. 问“我的 O1001 订单到哪里了？”，等到页面显示“回复已保存”。
2. 保持这个浏览器标签页打开。若服务由你在终端启动，在该终端按 `Ctrl+C`，再运行同一条启动命令。
3. 刷新原来的标签页，应能看到刚才的问题、回答，以及“已恢复保存的对话”。
4. 继续问“这笔订单买的是什么？”，模型应能结合前文回答“无线键盘”。

还可以点击“新对话”，确认列表新增一项，再点回原来的会话。选中旧会话后关闭标签页，重新打开同一个网址，应继续选中它。新建和清空是不同的操作。

每条历史会话旁都有“删除”按钮，确认后会永久删除这段会话及其消息。删除当前会话后自动切换到剩余会话；删掉最后一段后，页面会创建一个空会话。删除其他会话会保留当前草稿与阅读位置，生成回复期间禁止删除。

长对话只在聊天内容区滚动，输入框保持可见。处于底部时自动跟随流式回复；向上滚动阅读历史后暂停跟随，并出现“回到底部”按钮，点击后恢复跟随。

O1001 开头是英文字母 **O**。订单仍来自 `orders.py` 的模拟数据；模型问答会调用原有 DeepSeek 配置。

默认数据库位于：

```tex
.\data\chat.db
```

首次启动会自动创建目录和表，后续启动会沿用已有文件。数据库路径由 `api_app.py` 所在目录计算，不取决于你从哪个终端目录启动程序。

## 2. 三处“保存”各自保存什么

你熟悉 React state 和浏览器存储，可以用下面的对应关系理解：

| 位置 | 本课保存的内容 | 后端重启后的情况 |
|---|---|---|
| 浏览器 `localStorage` | 上次选中的 `session_id`，即会话编号 | 关闭标签页后仍可用这个编号恢复 |
| Python 内存 `app.state.sessions` | 已加载的完整历史缓存，以及 `busy` 忙碌状态 | 重新建立缓存，忙碌状态从空闲开始 |
| 磁盘 `data/chat.db` | 会话编号、创建时间、完整消息 | 已提交的数据保留，按编号重新读取 |

数据库保存所有会话；浏览器只记住上次选中的编号。点击网页的“新对话”会调用创建接口，生成新的编号并切换过去，原会话继续保留在列表中。清空仍是单独的 reset API，仅在明确调用时替换该编号的消息；网页的新建按钮不调用它。

页面先读取服务端列表，再恢复上次选中的会话。若浏览器编号被清理或已经失效，就选择列表中最新创建的会话；只有数据库里没有任何会话时才自动创建。升级前仍打开的标签页会把旧 `sessionStorage` 编号迁移到 `localStorage`。不同浏览器或不同网址来源的浏览器存储彼此独立，但同一服务的 SQLite 记录仍可通过列表找到。

## 3. 代码新增了哪一层

```text
网页发送 {session_id, message}
            ↓
api_app.py 找到会话
    内存没有 → session_store.py 从 SQLite 加载
            ↓
agent_service.py 携带完整历史请求模型、执行订单工具
            ↓
得到一轮完整消息
            ↓
session_store.py 在事务中保存 → 成功后更新内存缓存
            ↓
JSON 返回回答 / SSE 发出 done → 网页显示“回复已保存”
```

先按下面的顺序阅读，连接清理和取消保护可以放到第二遍：

| 文件与位置 | 第一遍理解什么 |
|---|---|
| [session_store.py](../session_store.py) 的 `initialize()` | 数据库有哪两张表 |
| 同文件的 `create_session()`、`list_sessions()`、`load_session()` | 怎样新建、列出摘要、读取完整消息 |
| 同文件的 `replace_history()` | 为什么删除和插入必须在同一个事务中 |
| [api_app.py](../api_app.py) 的 `get_session()` | 重启后如何从数据库重新加载 |
| 同文件的 `persist_history()` 与聊天路由 | 为什么先保存成功，再报告完成 |
| [web/app.js](../web/app.js) 的 `initialize()` | 页面怎样用原编号恢复聊天区 |

`SessionStore` 是一个普通 Python 类。`__init__` 类似 TS 的 constructor，`self` 用于访问当前实例的属性。它只负责数据库操作，不需要知道 FastAPI 路由或模型 SDK 的细节。

## 4. 用两张表表示会话和消息

`sessions` 表每行代表一个会话：

| 列 | 含义 | 示例 |
|---|---|---|
| `session_id` | 会话的唯一编号，主键 | `a12b…`，这里省略完整 UUID |
| `created_at` | 创建时间，UTC 时间字符串 | `2026-09-12T04:59:10+00:00` |

`messages` 表每行代表一条消息：

| 列 | 含义 | 示例 |
|---|---|---|
| `session_id` | 这条消息属于哪个会话 | 与上表的编号对应 |
| `position` | 在完整历史中的顺序，从 0 开始 | `0`、`1`、`2` |
| `message_json` | 一条完整消息转成的 JSON 文本 | `{"role":"user","content":"查 O1001"}` |

消息表使用 `(session_id, position)` 作为联合主键：同一会话的同一位置只能有一条消息，不同会话都可以从位置 0 开始。

外键规定消息所属的会话必须存在。代码在每次连接上启用 `PRAGMA foreign_keys = ON`。表中的 `ON DELETE CASCADE` 表示删除会话行时连带删除它的消息。`delete_session()` 利用这个机制在一个事务内删除会话和消息；reset 只替换消息，不删除会话行。

一次订单查询通常会得到这五条消息：

```text
position 0  system     系统指令
position 1  user       我的 O1001 订单到哪里了？
position 2  assistant  tool_calls：请求 get_order
position 3  tool       tool_call_id：对应调用的订单查询结果
position 4  assistant  面向用户的最终回答
```

网页只展示问答正文，但下一轮模型请求需要包含工具调用与工具结果。因此代码保存整个消息字典，包括 `tool_calls`、`tool_call_id` 和嵌套字段。不能只从网页聊天气泡提取文字来恢复模型上下文。

## 5. Python 对象、JSON 文本和 SQL 是三件事

保存时的核心转换是：

```python
text = json.dumps(message, ensure_ascii=False)
```

`message` 是 Python 字典，`text` 是字符串。它相当于 TS 中的 `JSON.stringify(message)`。`ensure_ascii=False` 让中文保留为可读字符。

读取时用 `json.loads(text)` 还原字典，类似 `JSON.parse(text)`。工具参数或工具结果本身也可能是 JSON 字符串，保存完整消息会忠实保留这种嵌套关系，不会把工具参数擅自改成另一种类型。

真正把数据交给数据库的是 SQL，例如：

```python
session = connection.execute(
    "SELECT session_id, created_at FROM sessions WHERE session_id = ?",
    (session_id,),
).fetchone()
```

这里逐项理解：

- `SELECT` 表示查询；`WHERE` 指定只查询这个编号。
- `?` 是参数占位符；编号通过第二个参数传入，不拼进 SQL 字符串。
- `(session_id,)` 是只含一个元素的元组，末尾逗号不能省略。
- `fetchone()` 取一行，查不到时返回 `None`。
- 连接配置了 `sqlite3.Row`，因此可以写 `session["created_at"]` 读取列。

读取消息还加了 `ORDER BY position`，明确按原来的顺序恢复。数据库查询结果不能只凭“插入时就是这个顺序”来推断排序。

保存多条消息时，列表推导式先准备参数：

```python
rows = [
    (session_id, index, json.dumps(message, ensure_ascii=False))
    for index, message in enumerate(history)
]
```

`enumerate(history)` 同时给出下标和元素，可以类比 TS 的 `history.map((message, index) => ...)`。后面由 `executemany(sql, rows)` 对这些参数执行同一种插入语句。

## 6. 为什么保存要使用事务

本课为便于理解，每次保存都替换这个会话的完整历史：先删除旧消息，再插入新列表。如果插入到一半失败，旧记录也必须保留。

事务把这些操作作为一个整体：

```text
开始事务
  DELETE 当前会话的旧消息
  INSERT 完整历史的所有消息
全部成功 → commit，提交这一组变化
任一步失败 → rollback，撤销本次删除和插入
```

代码使用了两个不同的上下文管理器：

```python
with closing(self._connect()) as connection, connection:
    # 在这里执行本次数据库操作
    ...
```

从内向外退出时，`connection` 负责成功提交或异常回滚；`closing(...)` 负责最终关闭连接。数据库连接的 `with` 本身不会关闭连接，这是容易漏掉的细节。[Python sqlite3 文档](https://docs.python.org/3/library/sqlite3.html#how-to-use-the-connection-context-manager)说明了这两种职责。

`_connect()` 先在事务外启用外键，再设置 `autocommit=False`，让操作按需要提交或回滚的事务方式执行。消息先转成 JSON，再进入数据库事务；模型网络请求也在事务外完成，避免等待模型时一直占用数据库。

`replace_history()` 先执行写操作取得写锁，再检查会话是否存在。这样可以避免多个连接都先读取、随后争抢把读锁升级为写锁。这里的 DELETE 即使已经执行，后续失败也会随同一事务回滚。

测试使用临时数据库模拟“删除后，插入到一半失败”的情况，测试确认旧历史完整保留。测试文件是 [tests/test_session_store.py](../tests/test_session_store.py)。

## 7. 完整回复什么时候算保存成功

一轮模型输出会先逐段显示，但只有模型完整结束后才得到可保存的历史。接口按下面的顺序处理：

```text
完整模型结果 → 数据库提交成功 → 更新内存 → 返回成功响应
```

| 发生的情况 | 已保存历史怎样变化 |
|---|---|
| 模型报错、结果截断，或开始保存前收到断连取消 | 保留上一轮已完成的历史 |
| 数据库写入失败 | 事务回滚，内存也不更新 |
| 数据库提交成功，完成响应正常送达 | 页面显示“回复已保存” |
| 数据库已提交，但最终网络发送失败 | 完整回合已经保存，刷新后可恢复 |

所以页面没收到 `done` 时，不能简单推断数据库一定没保存。当前网页提示先刷新确认保存内容，再决定是否重发；这一课没有加入自动重试去重功能。

JSON 接口的数据库错误返回 HTTP 503。SSE 若已开始发送响应，就使用 `error` 事件报告保存失败，不发出表示成功的 `done`。

第二遍读代码时，再看两个资源管理细节：

- `anyio.to_thread.run_sync(...)` 把同步数据库操作放到工作线程。等待数据库锁时，事件循环仍可处理健康检查等请求。每个方法在自己的线程内创建、使用并关闭连接，不把同一个连接交给不同线程。
- 保存前先执行一个取消检查点；一旦开始短数据库事务，就在取消保护范围内等它结束并同步缓存，最后才释放 `busy`。否则后台线程还在写入，前台却可能开始下一轮，造成覆盖。

JSON 和 SSE 的保存操作都在断连监听范围内。即使断连恰好发生在模型连接的关闭清理阶段，清理结束后也会先检查取消，再决定能否开始保存。

## 8. 八个接口如何使用数据库

| 接口 | 本课行为 |
|---|---|
| `GET /api/health` | 增加 `storage: "sqlite"`，表示当前存储方式 |
| `POST /api/sessions` | 创建独立会话及初始 system 消息，成功后返回 201、编号和创建时间 |
| `GET /api/sessions` | 返回所有会话的编号、创建时间和标题，供历史列表使用 |
| `GET /api/sessions/{session_id}` | 必要时从数据库加载；返回完整 messages、busy 和 created_at |
| `DELETE /api/sessions/{session_id}` | 删除会话及消息，成功返回 204；不存在返回 404，忙碌返回 409 |
| `POST /api/sessions/{session_id}/reset` | 在事务中将消息替换为初始 system 消息 |
| `POST /api/chat` | 保存完整回合后返回 JSON |
| `POST /api/chat/stream` | 逐段输出，保存完整回合后发出 done |

`list_sessions()` 使用原来的两张表，无需更改数据库结构。它通过 `LEFT JOIN` 同时列出已有问答和空会话；标题取 position=1 的第一条用户消息，只读取摘要，选中时再 GET 完整历史。标题最多显示 40 个字符，较长的问题仍完整保存在原消息中。

删除也使用 `busy` 防止与生成、清空同时操作。数据库提交成功后才移除内存缓存，失败则保留历史。冷加载和删除共用一把异步锁，避免旧读取在删除后把会话重新放回缓存。其他标签页等待生成时若读到 404，网页会解除忙碌状态并恢复可用会话。

可以在[接口文档](http://127.0.0.1:8000/docs)中练习：先创建会话，复制返回的 `session_id`，发送聊天请求，再按这个编号查询历史。`created_at` 使用 UTC，字符串末尾的 `+00:00` 表示时区偏移。

`busy` 仍是单个 Python 进程内的协调标志，因此继续使用当前单进程启动方式。本课也没有登录和用户权限系统，服务继续只监听本机地址。

本机数据库已加入 `.gitignore`，也没有挂载为网页静态文件。不要用文本编辑器修改 `chat.db`；需要查看数据时，可以先通过会话 GET 接口读取 JSON。未持久化的内存历史无法在重启后恢复。
