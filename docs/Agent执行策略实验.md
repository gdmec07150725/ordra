# Agent 执行策略实验

这一入口复用现有 Agent API、LangGraph 执行过程、MCP 工具、结果校验和评测用量统计，研究同一问题应该由主管直接处理还是委派子 Agent。它不是模型训练，也不会自动修改正式聊天策略。

## 运行

在项目目录运行，默认只使用脚本模型，不请求模型服务：

```powershell
.\.venv\Scripts\python.exe -X utf8 .\decision_eval.py
```

默认 6 个案例 × 3 种策略 × 每组 3 次，共 54 次。实际运行本地 MCP 和临时数据库；模型决策、校验及 token 用量为脚本，仅验证两种执行路径、故障恢复和报告逻辑，不能据此比较策略质量或模型成本。

真实模型对照需要显式加 `--live`，使用已有模型配置，会消耗模型额度。可以先缩小范围：

```powershell
.\.venv\Scripts\python.exe -X utf8 .\decision_eval.py --live --case simple_order --case order_policy --repeats 3 --output .local/evals/decision-live.json
```

`--case` 可以重复；`--strategy current --strategy direct` 可以只比较两种策略。`--repeats` 为 1～10，默认 3；`--timeout` 是每次执行的秒数上限，默认 90。失败和超时计入通过率分母，程序退出码为 1；它们是实验结果，不一定是评测程序故障。

JSON 和同名 HTML 报告写入 `.local/evals/`，每完成一次试验更新一次。中断时已有文件明确显示未完成；再次运行会重新实验，不接续旧试验。默认文件名带时间；显式指定同一路径会替换旧报告。

修正评分规则后，可统一复核已有回答，无需再次请求模型。必须写入另一文件，保留初始报告：

```powershell
.\.venv\Scripts\python.exe -X utf8 .\decision_eval.py --regrade .local/evals/decision-live.json --output .local/evals/decision-live-regraded.json
```

复核报告记录原报告指纹、评分代码指纹、前后变化及时间。不要只修改失败样本的分数。旧报告若没有记录子 Agent 在执行前被拒绝的响应，其无效调用只能按已保存的执行轨迹统计，报告会标注覆盖不足。

## 固定条件与唯一变量

| 策略 | 唯一新增的执行偏好 |
| --- | --- |
| current | 沿用当前系统规则，不附加偏好 |
| direct | 优先由主管直接查询，可并行执行独立只读工具 |
| selective | 订单事实与政策资料独立时委派两个子 Agent，简单问题直接处理 |

每次独立会话，保持相同模型、上下文预算、Skills、审批、工具、知识夹具和结果校验。偏好加入 system 消息，正常计入上下文预算；不通过禁用工具强迫模型选路线。所有策略都能调用相同工具。报告单独给出实际路线与策略遵循率，任务正确但没有遵循偏好也如实展示。

在每个案例和每轮重复中轮换策略先后顺序，减小固定先后顺序的影响；小样本无法排除缓存、服务负载和模型随机性的影响，不能当成统计显著结论。

临时政策和模拟订单都不是生产业务事实。知识检索固定为关键词模式，不评测 Embedding 召回质量；不会读写正式聊天数据库。历史案例使用固定的合成 O1001 回合，重现旧工具发现状态可能干扰新任务的问题，不导出或重放用户私有聊天。

## 案例和判据

| 案例 ID | 检查内容 |
| --- | --- |
| simple_order | O1003 实际查询与签收状态回答 |
| order_policy | 原故障问题的控制复现，要求订单事实、政策原文、退款条件与待补充信息 |
| history_discovery | 相同问题前加入旧订单查询、工具发现记录，检查本轮重新获取证据 |
| missing_reason | 缺少具体退货原因时询问，不能尝试生成预览 |
| missing_order | 未提供订单号时询问，不能猜测订单进行查询 |
| tool_transient | 首次订单工具调用注入一次连接错误，随后真实调用工具，检查运行时重试成功 |

工具成功、原文证据、保存结果与回复规则共同决定通过，并要求现有模型校验通过；不会只根据模型说“完成了”评分。关键词规则是有限的覆盖检查，模型校验也可能出错，重要业务回答仍应人工抽查。

无效调用记录参数、未发现工具和控制协议拒绝；重复调用按同一回合同名同参数统计（排除计划更新），合理复查也可能计入，因此不直接等同任务失败。

模型请求数从实际 HTTP 请求观察，包含主管、子 Agent、结果校验、摘要以及实际发送的重试。tokens 仅使用服务端报告值；存在遗漏就不计算完整平均 tokens，保留部分已报告总量与覆盖情况。耗时包括模型和工具等待，失败和超时保留在统计中；环境尚未执行的试验不当作零耗时，相关平均效率留空。没有模型价格表，不估算金额。

## 如何据此改进

1. 先看每个案例每种策略的重复结果，以及具体失败判据。
2. 再看策略是否真的被执行，避免把自由选择的结果当成强制路线对照。
3. 对通过的业务目标比较全部模型请求、完整用量与耗时；同时检查简单查询、缺失信息和故障恢复是否退化。
4. 一次修改工具描述、反馈或策略中的一个因素，再运行相同案例。保留旧报告，核对案例、配置和代码指纹。
5. 扩大真实模型样本并人工复核，再决定是否改正式策略。本入口不会根据某次最快或离线全部通过自动选择赢家。

关键文件为 `eval_decision_scenarios.py`（案例与策略）、`decision_eval.py`（隔离运行、判据、统计）、`eval_decision_report.py`（报告）。原 `agent_eval.py` 的默认套件与 `--suite all` 保持原范围，避免常规回归意外增加几十次真实模型请求。
