## 2. 与上一课相比，返回值变了什么

上一课：

```python
# 等待完整响应对象。
response = client.chat.completions.create(
    model=model,
    messages=messages,
    stream=False,
)
answer = response.choices[0].message.content
```

本课核心结构：

```python
# 返回一个可以逐片读取的流。
with client.chat.completions.create(
    model=model,
    messages=messages,
    stream=True,
    stream_options={"include_usage": True},
) as stream:
    for chunk in stream:
        if not chunk.choices:
            continue
        text = chunk.choices[0].delta.content
        if text:
            print(text, end="", flush=True)
```

这个简化片段展示文字读取；完整示例还传入工具、关闭思考模式，并组装工具参数、检查结束状态和保存历史。

DeepSeek 使用 SSE 事件流发送增量结果。SDK 负责解析网络事件，你在 Python 中拿到的是 `chunk` 对象，不需要自己拆解原始 `data:` 文本。[DeepSeek 对话补全接口说明](https://api-docs.deepseek.com/api/create-chat-completion/)

## 3. 理解 chunk、delta 和 print

| 写法 | 本课中的含义 |
|---|---|
| `stream` | 可以不断读取后续片段的响应流 |
| `chunk` | 本次收到的一个片段对象 |
| `chunk.choices[0].delta` | 第一个候选在这个片段中的新增内容 |
| `delta.content` | 新增的回复文字，可能为空 |
| `end=""` | 打印后不自动换行，让相邻文字片段接起来 |
| `flush=True` | 立即刷新输出缓冲区，让文字及时显示 |

一个片段不一定对应一个字或一个 Token。它可能包含几个字，也可能只携带工具参数、结束状态或用量信息。

`for chunk in stream` 是同步读取：下一片还没到时会等待。流式输出不等于异步并发；当前仍然是模型完成后，再接受下一次输入。

## 4. 为什么工具参数需要拼接

模型提出的 `arguments` 也可能分几次到达，例如：

```text
片段 1：{"order_id":
片段 2："O1001"
片段 3：}

拼接后：{"order_id":"O1001"}
```

因此本课在读取流时只收集工具请求，等整个响应结束，再检查状态与参数，然后执行 `get_order()`。

```python
# += 对字符串表示连接，把后续参数片段追加到已收集的内容后面。
call["function"]["arguments"] += part.function.arguments
```

如果同一个响应请求查询两笔订单，片段可能交错到达。代码使用 `calls_by_index` 字典分别保存它们：

```text
index 0 → 第一笔工具调用的名称、ID、参数
index 1 → 第二笔工具调用的名称、ID、参数
```

两个字段的用途不同：

- `index`：在当前响应里，把属于同一调用的片段拼在一起。
- `id`：响应收完后，用于把 `tool` 结果与 `assistant` 提出的调用配对。

参数凑成合法 JSON 还不代表模型已经完成输出。只有收到完整响应、结束状态为 `tool_calls`、调用 ID 和名称完整，并通过实际参数检查，程序才执行工具。

## 5. 显示中的文本与已保存的历史

本课同时维护两个结果：

```text
文字片段到达 → 立即打印到终端
             → 收集到 text_parts

正常结束 → 将片段合成完整回答 → 写入本轮 messages → 更新 history
```

关键代码：

```python
# 读取时收集片段。
text_parts.append(delta.content)

# 响应结束后，连接成一个完整字符串。
answer = "".join(text_parts)
```

`/history` 里保存的是完整的 `assistant` 消息，不会把每个字都存成一条消息。正常回复也只在终端显示一次，完成后不再重复打印整段正文。

如果网络断开、输出被长度上限截断或你按了 Ctrl+C，屏幕上可能已经显示了部分文字。程序会提示本轮未完成，并保留上一次成功的历史；已经显示的片段无法因此从终端“撤回”，但不会被当作完整回复加入上下文。

## 6. 为什么检查 finish_reason 和关闭流

`finish_reason` 说明模型为什么结束当前响应：

| 状态 | 本课处理 |
|---|---|
| `stop` | 收到非空文字时，保存完整回复 |
| `tool_calls` | 检查并执行收齐的工具请求，再请求模型 |
| `length` 等其他状态 | 提示本轮未正常完成，不执行截断的工具调用 |
| 没有收到结束状态就结束读取 | 视为不完整响应 |

这些结束状态来自接口协议。[DeepSeek 返回字段说明](https://api-docs.deepseek.com/api/create-chat-completion/)

`with ... as stream` 会在代码块结束或发生异常时关闭响应流。`read_stream()` 中的 `finally` 则负责在文字已经开始显示时补一个换行，让错误提示有独立的一行。

关闭本机响应流不保证远端立即停止生成，也不会撤销已经发生的请求或工具操作。本课继续关闭自动重试，失败后由用户决定是否重新提问。

Token 用量在收到统计片段后统一显示。当前代码既能处理统计与结束状态放在同一片段的情况，也兼容空 `choices` 的统计片段。

## 7. 阅读顺序与小练习

先读 `read_stream()`，理解“收到一个片段就处理一次”；再读 `run_agent_turn()`，找出执行工具和更新 history 前的检查。`chat_loop()` 的输入命令与上一课相同，新增了流中错误和底层连接错误的处理。

可以做三个练习：

1. **观察流式文字。** 输入“请用四句话介绍 O1001 的状态，每句话单独一行”，观察回复出现的过程。不要用额外 sleep 延时模拟流式输出。
2. **检查完整历史。** 回复结束后输入 `/history`，确认最终回答是一条完整消息，工具调用与结果仍然配对。
3. **尝试中断。** 在模型仍在生成较长回复时按 Ctrl+C，观察提示，然后输入 `/history`，确认失败的本轮没有写入成功历史。如果回答已经结束，Ctrl+C 会按等待输入时的规则退出程序。

课堂示例用于理解机制，仍然使用内存历史、本地模拟订单和最多 4 次模型请求的单回合上限。
