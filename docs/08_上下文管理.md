# 第八课：token 预算、滚动摘要与近期完整回合

> 本文按课程阶段讲解；请在仓库根目录执行命令。安装与当前功能以[仓库 README](../README.md)为准，早期章节中的简化流程不代表最终实现。

> 后续版本：[第九课](09_历史检索工具.md)已给网页增加按需关键词检索，模型可以查回摘要遗漏的原文；本课的预算与滚动摘要继续生效。`08_context_demo.py` 仍专门演示摘要，历史检索使用 `09_history_demo.py`。

这一版已经替换网页原来的“最近 6 轮”策略。现在由内容长度决定是否压缩：短对话直接完整带入；超预算时，较早的完整回合合入摘要，近期回合尽量保留原文。

你可以先把这三个对象区分开：

| 对象 | 保存什么 | 用途 |
|---|---|---|
| `history` | 全部成功回合，包括工具请求和结果 | 网页展示、重启恢复、后续可做历史检索 |
| `ContextMemory` | 滚动摘要 + 已覆盖到哪个消息位置 | 避免每次重新摘要整段历史 |
| `messages` | 本次实际给模型的内容 | 控制单次上下文大小 |

摘要不会替代数据库的原文。`context_window.py` 仍保留为固定轮数的对照示例，正式接口已不再使用它。

## 1. 先运行离线演示

```powershell
# 在仓库根目录运行
.\.venv\Scripts\python.exe -X utf8 .\08_context_demo.py
```

演示构造 10 轮历史，订单号只出现在第一轮。默认演示总预算 4300、近期目标 500，便于快速观察压缩。**离线摘要是写死的演示文本，不是模型生成的**；它只帮助你理解边界选择、预算计算和消息拼接。

你会看到：

- 原始历史有 23 条消息。
- 较早 9 轮分批合入摘要，最近 1 轮保留原文。
- 发给模型的结构是 system → 历史摘要 → 最近 user/assistant → 当前 user。
- 原始 23 条消息仍全部存在。

也可以比较不同预算：

```powershell
.\.venv\Scripts\python.exe -X utf8 .\08_context_demo.py --budget 8192 --recent 2048
```

这组演示历史在较大的预算内能够完整放下，因此不会调用摘要。这说明算法按长度触发，没有固定到第几轮就删历史的规则。

## 2. 每次请求怎样组装

```text
完整 SQLite 历史 + 上次摘要 + 当前问题/本轮工具消息
                         ↓
       system + 摘要 + 未摘要的完整回合 + 当前回合
                         ↓
    估算输入 + 回答预留 + 安全余量 是否超过总预算？
             否                        是
             │               选择较早的完整回合
             │                        ↓
             │              旧摘要 + 新的较早回合
             │                        ↓
             │              摘要模型生成新的摘要
             │                        ↓
             │                 重新组装并检查
             └─────────────┬──────────┘
                           ↓
                     调用回答模型
                           ↓
                 工具请求？执行后再次检查预算
                           ↓
             最终回答成功 → 历史与摘要一起提交
```

`agent_service.py` 用 `active` 单独记录当前回合。调用工具后，active 会同时包含工具请求和对应结果；下一次模型请求仍要重新执行 `prepare()`。

```python
active = [{"role": "user", "content": question}]

# 每一轮模型/工具往返之前都执行，不仅是第一次提问。
async for event in context.prepare(client, model, active):
    yield event

# context.messages 是给模型的短上下文。
# 成功落盘仍是完整原文，不把摘要冒充原始消息。
full_history = history + active
```

## 3. token 预算到底怎么算

网页默认配置如下。没有配置这些新变量时也会使用默认值，无须修改现有 `.env`。

```dotenv
AGENT_CONTEXT_TOKENS=8192
AGENT_RECENT_TOKENS=2048
AGENT_SUMMARY_TOKENS=512
```

默认可用输入预算：

```text
8192 总预算 - 512 回答输出预留 - 256 安全余量 = 7424 输入预算
```

输入估算包含 system、摘要、历史、当前问题、工具定义、工具调用参数和结果。工具调用后新增加的消息也计入。摘要模型自己的输入也会检查，较长的旧历史按完整回合分批处理。

这里的 8192 是**应用自己设定的预算**，不是在声明 DeepSeek 的最大上下文窗口。输出预留 512 和安全余量 256 在 `ContextPolicy` 中定义。

当前没有引入模型专用 tokenizer。`estimate_request()` 使用“序列化 JSON 的 UTF-8 字节数 ÷ 2 向上取整 + 64 格式余量”估算常见中英文内容。这个方法倾向于多留空间，但**不是精确分词，也不保证对任意文本都高估**。安全余量同样不能将估算变成数学保证。网页明确显示“估算输入”；模型响应中的 `usage` 才是实际报告的 tokens。未来要接近模型窗口上限使用时，应换成与具体模型匹配的 tokenizer，并校准消息和工具格式开销。

配置会检查基本范围：总预算至少 2048，近期目标至少 128，摘要预算至少 256；近期目标和摘要预算之和必须小于可用输入预算。实际必需消息仍会在每次请求前检查。

修改环境变量后需要重启 Python 服务。旧的 `AGENT_CONTEXT_TURNS` 不再参与正式接口，可以移除；配置方式见仓库 README。

## 4. 近期完整回合不是固定轮数

触发压缩时，程序从最近的已完成回合往前选，尽量把原文控制在 `AGENT_RECENT_TOKENS` 目标内。

一轮可能只有 user + assistant 两条，也可能是：

```text
user
assistant(tool_calls: a, b)
tool(result for a)
tool(result for b)
assistant(final answer)
```

这五条属于同一轮。不能为了凑预算留下工具结果却丢掉请求，也不能只保留 a 却丢掉同批 b。

近期值是目标，不是精确条数或硬上限：一个略大的最近回合能放入总预算时，仍完整保留；总空间不足时，会继续按完整回合缩小原文后缀，极端情况下已完成历史全部进入摘要。当前正在生成的回合始终保留，不能从中间裁掉工具消息。

没有触发压缩时，即使未摘要历史超过近期目标，也会继续完整带入。近期目标控制的是“压缩后留多少”，总预算决定“何时需要压缩”。

## 5. 什么叫滚动摘要

首次压缩：

```text
第 1～7 轮原文 → 摘要 A
```

后续继续聊天，再次超预算：

```text
摘要 A + 新进入压缩区的第 8～12 轮 → 摘要 B
```

无需重新读取第 1～7 轮给摘要模型。`ContextMemory.covered_messages` 保存原始列表的**排他上界**：

```python
memory = ContextMemory(text="用户提供订单 O1001……", covered_messages=15)

# history[:15] 已被摘要覆盖；history[15:] 仍保留原文。
```

这个位置是消息下标，不是轮数。它必须落在下一条 user 的开头或完整历史末尾，不能切到 assistant/tool 中间。

摘要提示词要求保留订单号及指代、用户要求与偏好、明确更正、已作决定、未解决问题，并记录不确定性。工具结果和历史摘要都只是数据，不能成为新的系统指令。订单状态可能过期，摘要不能充当实时业务数据源。

## 6. 为什么摘要单独存表

`messages` 表继续保存完整原文，新增 `context_memory` 表只保存：

```text
session_id | summary_text | covered_messages
```

服务启动使用 `CREATE TABLE IF NOT EXISTS` 添加表，旧会话无摘要时从空记忆开始，不需要删除或重建数据库。

`SessionStore.replace_history(session_id, history, memory)` 在同一事务中提交完整历史与摘要。只有提交成功后才更新内存 Session、向网页发送 done。

这保证了：

- 摘要或回答失败：原历史和旧摘要不变。
- 摘要生成期间断连：取消请求、释放 busy，不提交草稿。
- 数据库写入失败：历史和摘要一起回滚。
- 提交后 done 发送失败：刷新仍能恢复已提交的回答与摘要。
- 重启或切换会话：恢复该会话独立的摘要，不串会话。
- reset 清空历史时也清空摘要；删除会话时外键级联删除两者。

`frozen=True` 的 dataclass 类似 TypeScript 中只读的记录：更新摘要时创建新的 `ContextMemory`，不会修改调用方传来的旧对象。这个设计配合事务，避免失败途中悄悄推进摘要位置。

## 7. 网页怎样观察

网页入口和启动方式不变：

```powershell
.\.venv\Scripts\python.exe -X utf8 .\07_api_server.py
```

打开 [本地聊天页面](http://127.0.0.1:8000)。短聊天不一定立即触发摘要，这是正常行为。

触发时会出现“正在整理对话记忆”。回答下方显示最近一次回答模型请求的估算输入、输入预算、保留原文的轮数、摘要覆盖的轮数，以及模型实际报告的用量。

回答阶段和摘要阶段的 usage 分开累计。工具循环可能带来多次回答模型请求；长历史也可能需要多次摘要请求。某次响应没有提供 usage，就不把缺失值当成已知零用量；页面会标明已报告次数。统计说明当前只在本次回复后展示，刷新历史时不会重放以前的统计。

摘要本身也花 tokens，并增加触发时的等待时间。一次压缩不保证本轮总成本更低；它的主要作用是控制之后持续聊天的上下文大小。

## 9. 和 LangChain 的关系

LangChain 的 [context engineering](https://docs.langchain.com/oss/javascript/langchain/context-engineering) 讨论每一步 Agent 调用如何获得合适的信息、工具和状态；历史管理只是其中一部分。

官方 [SummarizationMiddleware](https://docs.langchain.com/oss/python/langchain/middleware/built-in#summarization) 提供按阈值触发摘要、保留近期消息等机制。我们采用相同方向，在现有 Python 代码中显式实现预算、完整用户回合、滚动摘要和数据库事务，便于逐步理解；这里没有直接调用该中间件。LangChain 的“保留 messages”也不天然等于本例的“保留完整用户回合”。

本课阶段尚未实现按问题召回旧原文；该能力已在后续第九课通过关键词工具加入。当前仍未实现向量检索或跨会话长期记忆。摘要是有损压缩；完整日志保留下来，之后才有条件加入历史检索。

## 10. 失败边界与阅读顺序

如果当前问题及当前工具消息自身已经超过输入预算，或单个旧回合连摘要请求也放不下，程序会明确报预算错误，保留已保存记录。它不会静默截断文本。可以缩短当前问题，或合理增加 `AGENT_CONTEXT_TOKENS`；特别长的单条历史需要后续增加分段压缩能力。

摘要为空、被模型截断、或仍超出摘要估算上限时，本轮失败并提示重试。代码不会把半段摘要当作完成结果保存。

建议阅读：

1. `08_context_demo.py`：构造历史，区分离线固定数据与真实模型。
2. `ContextPolicy`、`ContextMemory`：配置和需要持久化的状态。
3. `RollingContext.compose()`：消息到底怎样拼接。
4. `RollingContext.prepare()`：预算判断、完整回合边界、增量摘要。
5. `agent_service.py`：每个工具循环前检查，最终只追加 active。
6. `session_store.py`、`api_app.py`：事务提交、重启恢复与失败清理。
