# 第四课：连续对话与会话历史

> 本文按课程阶段讲解；请在仓库根目录执行命令。安装与当前功能以[仓库 README](../README.md)为准，早期章节中的简化流程不代表最终实现。

本课让同一个程序持续接收问题，并把已经完成的对话用于下一次请求。你可以先说“帮我查订单”，再补充“订单号是 O1001”。

主文件：`.\05_chat_agent.py`。本课复用 `.env`、模型客户端和模拟订单数据；新环境请先按仓库 README 完成配置。

## 1. 启动后，直接输入问题

在仓库根目录打开 CMD 后执行：

```bat
rem 在仓库根目录运行
.\.venv\Scripts\python.exe -X utf8 .\05_chat_agent.py
```

PowerShell 也可以在仓库根目录运行相同的 Python 命令。

程序显示 `你：` 后，输入下面的第一句话，等待回复后再输入第二句。此时输入内容不需要加引号：

```text
帮我查订单
订单号是 O1001
```

示例目标是：第一轮询问订单号；第二轮收到 O1001 后调用 `get_order`，再依据工具结果回复。

这段对话中，三次模型请求分别携带了 2、4、6 条消息；最终历史共 7 条。生成的具体文字和用量可能变化。

## 2. 三个本地命令

| 输入 | 作用 |
|---|---|
| `/history` | 显示当前已完成的消息列表，包括工具调用和结果 |
| `/reset` | 开始新会话，只保留初始化的 system 消息 |
| `/exit` | 结束程序 |

这些命令由 Python 直接处理，不会发给模型。空输入也不会发请求。

等待输入时按 Ctrl+C，会退出程序；等待模型时按 Ctrl+C，会中断本轮等待，回到输入提示。已经发出的远程请求可能仍在服务端处理中。

**当前历史只保存在本次运行的内存中。** 关闭程序后重新启动，会从新会话开始；`/reset` 清空的是本地上下文，不是调用远程服务的数据删除接口。

## 3. 为什么保留 history 就能继续聊天

DeepSeek 的 `/chat/completions` 接口要求应用程序在每次请求中提供需要使用的历史上下文。复用同一个 `client` 本身不会让接口自动续接对话。[DeepSeek 多轮对话官方说明](https://api-docs.deepseek.com/zh-cn/guides/multi_round_chat/)

第一轮请求：

```text
system：订单客服的任务要求
user：帮我查订单
```

第一轮成功后，保存回复。第二轮再加入新问题：

```text
system：订单客服的任务要求
user：帮我查订单
assistant：请提供您的订单号……
user：订单号是 O1001
```

模型看到前后文，才能知道 O1001 是对刚才问题的补充。然后仍按第三课的流程，提出工具请求、接收查询结果、生成回答。

最终 history 中的顺序为：

```text
1. system：客服要求
2. user：帮我查订单
3. assistant：请提供订单号
4. user：订单号是 O1001
5. assistant：请求 get_order，携带调用 ID 和参数
6. tool：对应这个调用 ID 的订单数据
7. assistant：根据订单数据生成的回复
```

这里的“记得前文”来自请求里的消息上下文，没有训练模型，也没有修改模型参数。

## 4. 外层循环与内层循环

本课有两个循环，分别解决不同问题：

```text
chat_loop()：外层 while True
    读取用户的一次输入
    ↓
    run_agent_turn()：内层 for
        请求模型
        ├─ 请求工具 → 执行 → 回传结果 → 再请求模型
        └─ 给出回复 → 保存完整本轮消息 → 返回
    ↓
    等待用户的下一次输入
```

外层循环让程序持续运行；内层循环让同一个问题可以完成工具调用。一个用户回合可能包含多次模型请求，这两种“轮次”需要分开理解。

每个用户问题最多请求模型 4 次，下一个用户问题重新计数。当前采用同步调用，模型完成回答后再接收下一次输入。

## 5. 重点读这四处代码

**第一处：在输入循环外创建历史。**

```python
history = new_conversation()

while True:
    question = input("\n你：").strip()
    # 使用这个 history 处理当前问题。
```

`input()` 显示提示并等待回车，返回字符串；`while True` 表示持续循环，直到函数遇到退出分支。如果把 `new_conversation()` 放到每次提问的分支里，前文就会在下一次输入时丢失。

**第二处：复制已完成的历史，再加入本次问题。**

```python
messages = history.copy()
messages.append({"role": "user", "content": question})
```

`messages` 是本轮处理中的列表，`history` 是已经完成的会话记录。这里是浅拷贝：列表独立，但已有消息字典仍然被共享。本课只往新列表追加消息，不修改那些旧字典，因此足够使用。

**第三处：把模型的最终回答也保存下来。**

```python
messages.append({"role": "assistant", "content": message.content})
```

第三课只需要完成一次问题，最终回复打印后就退出。本课还需要保存这段回复，下一次模型请求才能知道助手之前说了什么。

**第四处：成功后更新原历史列表。**

```python
history[:] = messages
```

`[:]` 表示整个列表，切片赋值会把原列表的内容替换为 `messages` 的内容，调用方也能看到更新。

如果写成 `history = messages`，只是让这个函数里的局部变量改为引用另一个列表，外层持有的列表不会随之改变。结合 TypeScript，可以把这里的切片赋值类比为更新原数组的内容，例如 `history.splice(0, history.length, ...messages)`。

## 6. 请求失败后为什么还能继续

假设模型请求了订单工具，本机查询已经完成，但第二次模型请求超时了。如果直接把这些处理中消息留在长期使用的 history 中，后续可能混入没有完成的对话。

本课只在得到完整最终回答后执行 `history[:] = messages`。超时、服务端错误、回答截断、轮数超限或中断时，都保留上一次成功的历史，并提示重新提问。失败回合的用户问题也不会保存，需要重新输入。

这只控制本地消息列表。已经发送的 API 请求和已经执行的工具操作不会因此被撤销；当前订单工具仅查询模拟数据。

## 7. 按顺序做三个练习

1. **观察历史增加。** 启动后输入 `/history`，应只有 system。完成“帮我查订单”→“订单号是 O1001”后再输入 `/history`，寻找 user、assistant、tool，以及相互配对的工具调用 ID。
2. **验证前文的作用。** 继续问“我刚才提供的订单号是什么？”，观察模型是否能结合已保存的上下文回答。
3. **清空后比较。** 输入 `/reset`，再输入 `/history`，确认只剩 system。然后问“我刚才提供的订单号是什么？”，观察它与上一步的区别。

模型回答的具体措辞可能变化。判断历史机制是否生效，要看 `/history` 和发送的消息，而不只看某一句回复是否与你想象的一模一样。

对话越长，携带的上下文通常越多。本课保留完整历史，尚未加入摘要或长度裁剪；你可以先用 `/reset` 开始新会话。后续学习上下文管理时，再处理长对话。
