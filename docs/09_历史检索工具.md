# 第九课：让 Agent 按需检索历史原文

> 本文按课程阶段讲解；请在仓库根目录执行命令。安装与当前功能以[仓库 README](../README.md)为准，早期章节中的简化流程不代表最终实现。

这一课给网页 Agent 增加 `search_history` 工具。用户询问较早对话、当前摘要与近期原文不足以回答时，模型可以请求 Python 从当前会话的 SQLite 原文中查找依据。

第八课的 token 预算和滚动摘要继续生效。检索结果作为一条工具消息进入当前回合，也计入预算。完整历史仍然保存，不需要新数据库表或新的依赖。

## 1. 先运行离线演示

```powershell
# 在仓库根目录运行
.\.venv\Scripts\python.exe -X utf8 .\09_history_demo.py
```

演示会在临时数据库写入一条虚构原话：

> O1001 的收货时间要求：请周五18点之后再送达。

随后直接放入一份**故意遗漏收货时间的摘要**，用于稳定复现信息遗漏。这份摘要是演示数据，不是本次由模型生成的。

离线模式直接执行检索函数：查 `O1001 收货` 能找到原文；查 `发票 抬头` 得到空结果。另一个会话虽然有发票抬头，也不会被查出来。这个模式不请求模型，也不证明模型会选择工具，只验证检索函数的行为。

## 2. 模型怎样决定检索

我们把工具名称、描述和参数结构发给模型。工具说明告诉它：当问题需要旧对话依据、当前上下文不够时，可以使用历史检索；实时订单状态仍通过 `get_order` 查询。

```text
用户：我最开始对 O1001 的收货时间有什么要求？
              ↓
模型看到：摘要没有时间 + 近期对话也没有 + 可用 search_history
              ↓
模型返回工具调用请求：query="O1001 收货 时间", order="oldest"
              ↓
Python 搜索当前会话的 SQLite 原文
              ↓
工具返回：message:1，role=user，原文“……周五18点之后……”
              ↓
模型根据原文回答，并可标注来源
```

模型的工具选择不是确定性的条件判断，可能漏查或多查。这里保留 `tool_choice="auto"`，通过工具说明和系统规则引导；测试分别验证确定性的工具执行，以及小量真实模型的工具选择。没有加入“每个问题都必须先检索”的强制规则。

工具调用与实际执行的分工可对照 [DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)；由模型根据上下文选择工具的机制也见 [LangChain Tools](https://docs.langchain.com/oss/python/langchain/tools)。

## 3. 参数和关键词算法

模型可提供以下参数：

```json
{"query": "O1001 收货", "order": "oldest"}
```

`query` 是 1～100 字的字符串，包含 1～6 个简短关键词，以空格分隔。`order` 可省略，默认 `relevance`：

| 排序 | 用途 |
|---|---|
| `relevance` | 命中词越多越靠前，同等命中优先用户原话，再优先较新的消息 |
| `oldest` | 按原始消息位置从早到晚，适合找最初要求 |
| `newest` | 按位置从晚到早，适合查最近的说明或更正 |

当前实现是忽略大小写的关键词子串匹配。至少匹配一个关键词就会成为候选，不代表匹配全部词；模型仍需核对片段是否真正与问题有关。中文关键词需要主动拆开，例如 `收货 时间`；没有自动中文分词、同义词扩展或向量语义匹配。一次查不到时，模型可以换更短的词重查。

Python 用 `re.escape()` 把关键词当文字处理，不执行用户提供的正则。SQL 只使用参数化的当前会话编号，检索词不会被拼进 SQL。

## 4. 返回的原文如何核对

结果示意：

```json
{
  "query": "O1001 收货",
  "results": [{
    "source": "message:1",
    "position": 1,
    "role": "user",
    "text": "O1001 的收货时间要求：请周五18点之后再送达。",
    "start": 0,
    "end": 26,
    "truncated": false
  }],
  "matched_messages": 1,
  "has_more": false,
  "budget_limited": false
}
```

这是简化示意；实际查询也可能匹配助手的确认回复。

`message:1` 是当前会话原始消息列表的零基位置，第 0 条通常是 system。它不是网页上数到的第一个气泡，因为列表还包含工具请求和结果。`role` 区分用户原话与助手当时说的话；助手回复不能冒充用户要求。

长消息只截取命中处附近最多 240 个字符。`text` 始终等于原文的 `content[start:end]`，没有模型改写；`truncated` 表示片段不包含整条原文。这里只返回文字数据，不把检索到的旧消息重新作为可执行工具请求。

只搜索已成功保存的用户消息和助手最终回复。系统规则、工具结果及助手发起工具调用时的片段不会进入候选，因此也不会把以前检索返回的大段原文作为新的搜索结果反复套入。

## 5. 为什么模型不能指定别的会话

`session_id` 不属于工具参数。HTTP 路由先取得当前会话，再通过闭包绑定检索范围：

```python
def history_reader(session_id):
    async def search(query, order):
        return await anyio.to_thread.run_sync(
            store.search_history, session_id, query, order
        )
    return search
```

可以类比 TypeScript 的闭包：返回的函数只接收 `query/order`，但记住了外层的 `session_id`。实际代码在 `api_app.py`，会话编号由当前请求绑定。模型即使额外传入 `session_id`，也会被参数校验拒绝。

这里延续本机教学应用的会话隔离，并没有新增用户登录系统。SQLite 查询和关键词扫描在线程里运行，等待检索时其他会话和健康检查仍能响应。

## 6. 怎样控制检索的大小和次数

- 每次最多返回 3 条片段，工具结果自身控制在约 900 个估算 tokens。
- Agent 会收齐同批工具结果，再根据当前回合剩余预算统一减少历史片段，并为可能产生的摘要留空间。后续工具增加内容时，也可以回收本轮较早检索的片段。
- `matched_messages` 是命中的消息数；`has_more` 表示还有结果未返回；`budget_limited` 明确说明预算限制。
- 因预算而没有带回片段，不等于数据库里没记录，模型不能把这两种情况混为一谈。
- 一个用户回合最多实际搜索 3 次，沿用最多 4 次回答模型调用的限制。
- 工具调用与对应结果始终成对保存；下一次模型调用前仍会整体检查上下文预算。

检索是本地 Python 计算，本身不调用模型。不过模型选择工具、读取结果并生成回答，需要模型请求；返回的原文也会增加输入 tokens。

## 7. 失败与历史保存

数据库读取失败会返回错误，而不是伪装成空结果。检索参数有误时，工具返回参数错误，模型可以修正；真正没有关键词匹配时才返回空 `results`。

浏览器断连后等待正在运行的读取线程收尾，并在下一轮开始前检查取消，防止又发出新的模型请求。只有最终回答成功且事务提交完成，才保存本轮工具消息与回答。检索中断、模型输出不完整或写库失败时，之前的历史和摘要保持原状。

没有独立的搜索索引，所以 reset、删除会话后不会残留待同步的索引记录；重启后直接搜索已保存的原文。

## 8. 用真实模型观察

```powershell
.\.venv\Scripts\python.exe -X utf8 .\09_history_demo.py --live
```

这会使用现有 DeepSeek 配置，发起真实请求并消耗额度；仍然只使用临时演示数据库，不读写网页的会话。

终端会显示模型请求了哪个工具、实际返回的原文、最终回答和 token 用量。两个问题分别验证：收货要求能找回；发票抬头没有原文依据时，应如实说明。模型若没有调用历史检索，脚本会提示本次演示未通过，不会把直接回答当成检索成功。

网页仍运行 `07_api_server.py`，打开 [聊天页面](http://127.0.0.1:8000)。发生检索时会显示“正在查找之前的对话原文”，成功回答下方显示检索次数及带回的片段数量。统计只展示本次操作，刷新历史时不会重放旧统计。

## 9. 建议阅读顺序

1. `09_history_demo.py`：先看示例原文、故意遗漏的摘要和两个问题。
2. `history_search.py`：工具定义、参数校验、关键词匹配、排序与片段。
3. `SessionStore.search_history()`：按会话读取数据库。
4. `api_app.py` 的 `history_reader()`：闭包和工作线程。
5. `agent_service.py` 的 `execute_history_search()` 和工具循环：模型请求怎样变成 Python 执行。
